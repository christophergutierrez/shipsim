# Shipyard

Players assemble **ship classes** from components. A design compiles to an
ordinary `ShipDef` in `data/ships/`. Combat, scenarios, saves, and other
frontends load that file like any catalog hull. The engine stays the rules
authority; the yard does not reimplement hit tables.

The **TUI** is the authoring UI. The CLI compiles and checks files. A scenario
that uses a compiled class is a **fight**, not the yard.

## Run

From the repository root.

**Assemble / edit / create** (no map, no engine spawn):

```bash
cargo run --manifest-path frontend/tui/Cargo.toml -- --yard
```

**CLI** (never writes except `compile`):

```bash
cargo run --bin shipsim-yard -- validate data/designs/yard_destroyer.toml
cargo run --bin shipsim-yard -- cost data/designs/yard_destroyer.toml
cargo run --bin shipsim-yard -- compile data/designs/yard_destroyer.toml
```

**Fight** a compiled class (`scenarios/yard_destroyer.toml` is a duel):

```bash
cargo build -q
cargo run --manifest-path frontend/tui/Cargo.toml -- scenarios/yard_destroyer.toml
python3 frontend/repl/repl.py scenarios/yard_destroyer.toml
```

Love2D still has a yard (`./frontend/love/play.sh yard`); TUI `--yard` is the
product authoring path.

## TUI

Browse lists **class name**, **hull name** (Fighter, Destroyer, …), and **cost**.
The file id is not a browse column.

| Browse | |
|---|---|
| `↑`/`↓` `k`/`j` | Select a class, or **+ new ship** |
| `Enter` / `Space` | Edit the selected class, or start a new one |
| `n` | New class |
| `q` / `Esc` | Quit |

New classes get an **8-hex file token** (not 1, 2, 3 — deletes leave no holes)
and a unique default name `Basic Destroyer`, `Basic Fighter`, and so on. If
that name exists, `Basic Destroyer 2`. Changing hull size while the name is
still a `Basic …` default retitles it.

| Edit | |
|---|---|
| `↑`/`↓` | Next field (`j`/`k` too, except on the name) |
| type | Class name (first field). `↑`/`↓` leave it |
| `←`/`→` `h`/`l` | Change the focused field |
| `m` | Cycle weapon mount |
| `a` / `d` | Add / delete a weapon |
| `s` | Save design (not while the name is focused — `s` would type) |
| `c` | Save and compile to `data/ships/<id>.toml` |
| `Esc` | Back to the list |

Class **names** must be unique (case-insensitive, whitespace-normalized). The
name is the class, not an individual ship — several instances in a fight can
share one class.

## Identity and store

| Piece | Role |
|---|---|
| `id` | File token. `[a-z0-9_]+`. Stem of `data/designs/<id>.toml` and compile output `data/ships/<id>.toml`. Existing fixtures keep names like `yard_destroyer`; new work uses 8 hex. |
| `name` | Unique class label. Shown in the list and on the compiled ship. |
| Store | TOML under `data/designs/` today. A later sqlite catalog can replace that directory without changing the class-name rules. |

`compile` writes `data/ships/<id>.toml` atomically and only replaces a file
whose first line contains `# generated by shipsim-yard`. Stock and unmarked
catalog files are protected.

## Design schema

```toml
id = "yard_destroyer"
name = "Yard Destroyer"
size = 2
material = "titanium"
engine = "fission"
engine_size = "m"
armored = true
shields = [6, 4, 2, 2, 2, 4]   # F, FR, RR, R, RL, FL

[[weapons]]
component = "beam"
mount = "forward"
```

Unknown fields are rejected. Components live only in `data/components.toml`;
hull construction values live only in `data/sizes.toml`. Space and cost are
design-time; they are not combat resources.

## Hull size

Seven ids (combat silhouette **1–7**, baseline **2**). Construction space,
frame cost, and base HP follow MOO's four-hull decades on 1 / 3 / 5 / 7
(Small / Medium / Large / Huge), with geometric midpoints on 2 / 4 / 6.
Values are **×2 vs raw MOO Small** so a fighter can mount a compact gun.

`defense` is MOO natural defense. Combat still scales to-hit by `size / 2`,
then shifts the d20 by `(defense − size-2 defense)`. Path length is
`max_maneuver_actions` (`mv` in the TUI). No interstellar map.

| Size | Name | Space | Frame | Base HP | Defense | `mv` |
|---:|---|---:|---:|---:|---:|---:|
| 1 | Fighter | 20 | 4 | 2 | +2 | 8 |
| 2 | Destroyer | 63 | 9 | 6 | +1 | 8 |
| 3 | Light Cruiser | 200 | 20 | 20 | +1 | 7 |
| 4 | Heavy Cruiser | 632 | 63 | 63 | 0 | 6 |
| 5 | Battleship | 2000 | 200 | 200 | 0 | 5 |
| 6 | Dreadnought | 6325 | 632 | 632 | −1 | 4 |
| 7 | Titan | 20000 | 2000 | 2000 | −1 | 3 |

Thrust conversion (power → motion) is hull-derived and may be stepped by the
engine type (below). SSD `power_sys` / `engine_boxes` stay hull constants.

## Material

MOO armor line. Multiplies **structure** and **frame cost**. Tech is a label;
every material is always available (points-buy, no tech tree).

| Material | Tech | HP / frame |
|---|---:|---:|
| `titanium` | 1 | ×1.0 |
| `duralloy` | 9 | ×1.5 |
| `zortrium` | 17 | ×2.0 |
| `andrium` | 26 | ×2.5 |
| `tritanium` | 34 | ×3.0 |
| `adamantium` | 42 | ×3.5 |
| `neutronium` | 50 | ×4.0 |

## Engine

One **plant**: kind × size. Not a reactor spinner. Bigger sizes buy more
total power and take more space and money (worse per point). Fusion and
antimatter keep the same footprint as fission of that size, cost more, and
step the hull thrust ladder (`thrust_step` +1 / +2). That is combat speed,
not galactic travel.

| Size | Fission pwr/sp/c | Fusion | Antimatter |
|---|---|---|---|
| `s` | 6 / 6 / 12 | 8 / 6 / 20 | 10 / 6 / 32 |
| `m` | 14 / 22 / 36 | 18 / 22 / 58 | 24 / 22 / 90 |
| `l` | 36 / 64 / 110 | 48 / 64 / 180 | 64 / 64 / 280 |
| `h` | 80 / 160 / 300 | 110 / 160 / 480 | 150 / 160 / 750 |

A Large fission will not fit a Destroyer. Compiled `power` is the plant's
output; allocate spends from that pool.

## Armor

Yes/no hull wrap. **No interior space.** 1.5× hull HP after material. Cost
is half the material-adjusted frame (bigger / fancier hulls pay more).

## Shields

Per face, order **F, FR, RR, R, RL, FL**. One bank on a face is **one power
that face can hold** in battle. Each bank costs 1 and takes 1 space.

In the TUI, **shields all** steps every face together; `↓` onto a face to
set that face alone. Typical destroyer: `[6, 4, 2, 2, 2, 4]`.

Allocate still lights faces from 0 each turn, up to the banks on that face.
Compiled ships write `max_shields = […6…]` and `max_shield_per_facing` = the
max of those six. Stock catalog hulls with only the scalar keep one cap on
every face.

## Weapons

One `[[weapons]]` row per mount. `mount` is one of the six canonical values
(`forward`, `forward_starboard`, `aft_starboard`, `aft`, `aft_port`,
`forward_port`). The compiler derives `arc` (forward vs rear) from the mount.

SKUs live in `data/components.toml`. Compact is a space/cost trade and
compiles with `accuracy_bonus` / `damage_bonus` = 0. Potent and Precise write
those modifiers onto the compiled weapon.

## Formulas

```text
structure = round_half_up( base_structure × material.structure_mult × (armored ? 1.5 : 1.0) )
cost      = round_half_up( frame_cost × material.cost_mult )
          + (armored ? round_half_up(frame_cost × material.cost_mult × 0.5) : 0)
          + engine.cost + Σ shield_banks + Σ weapon.cost
space     = engine.space + Σ shield_banks + Σ weapon.space
            (must be ≤ hull.space; armor is 0)
thrust    = hull conversion, shifted by engine.thrust_step
```

Material multiplies the frame, not component prices.

## Fixtures

`data/designs/yard_*.toml` are committed examples (including
`yard_destroyer`). `scenarios/yard_destroyer.toml` is a duel that loads the
compiled class. Compiled `data/ships/yard_*.toml` are durable when a scenario
or suite names them. Throwaway experiments should stay uncompiled or be
removed after `compile`.
