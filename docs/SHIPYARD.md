# Shipyard CLI

The shipyard turns a component design into an ordinary `ShipDef` catalog file.
The engine remains the authority for validation and combat; existing scenarios,
saves, simulations, and frontends can load a compiled design like any other
ship class.

From the repository root.

**Assemble ships** (browse existing designs with cost, edit one, or create new).
This is not a fight and does not show a map:

```bash
cargo run --manifest-path frontend/tui/Cargo.toml -- --yard
```

**CLI** (validate / cost / compile a design file):

```bash
cargo run --bin shipsim-yard -- validate data/designs/yard_destroyer.toml
cargo run --bin shipsim-yard -- cost data/designs/yard_destroyer.toml
cargo run --bin shipsim-yard -- compile data/designs/yard_destroyer.toml
```

**Fight** a compiled class (`scenarios/yard_destroyer.toml` is a duel, not the
yard):

```bash
cargo build -q
cargo run --manifest-path frontend/tui/Cargo.toml -- scenarios/yard_destroyer.toml
python3 frontend/repl/repl.py scenarios/yard_destroyer.toml
```

Love2D: from the scenario picker press **Y** (or `./frontend/love/play.sh yard`)
to open the component shipyard. Compile shells out to `shipsim-yard`; Play
writes a scratch duel and reloads the engine.

`validate` and `cost` never write. `compile` derives the output as
`data/ships/<id>.toml`, writes atomically, and only replaces a file whose first
line contains `# generated by shipsim-yard`. Stock and unmarked files are
protected. The design filename stem must equal its lowercase `[a-z0-9_]+` ID.
New classes get an 8-hex file token (not a serial number, so deletes leave
no holes). The **class name** is what you edit and see in the list; it must
be unique. Defaults are `Basic Destroyer`, `Basic Fighter`, and so on.
TOML files under `data/designs/` remain the store; a later sqlite catalog
is optional.

Design sources live under `data/designs/`. They choose a hull size, material,
engine (kind + size), exterior armor (yes/no), shield banks, and one
canonical mount per weapon.

Power is a discrete **engine plant**, not a reactor spinner. Kind is the item
(fission / fusion / antimatter); size is S / M / L / H. Bigger sizes give more
power and take more space and cost (worse per-point). Fusion and antimatter also
step the hull thrust ladder (`thrust_step` +1 / +2) — partial conflate of
engine and combat speed, not galactic travel.

Hull material is the MOO armor line. It multiplies **structure** and **frame
cost** by the same factor. Tech is a label in the TUI; every material is always
available (points-buy, no tech tree).

| Material | Tech | HP / frame cost |
|---|---|---|
| `titanium` | 1 | ×1.0 |
| `duralloy` | 9 | ×1.5 |
| `zortrium` | 17 | ×2.0 |
| `andrium` | 26 | ×2.5 |
| `tritanium` | 34 | ×3.0 |
| `adamantium` | 42 | ×3.5 |
| `neutronium` | 50 | ×4.0 |

```text
structure = round_half_up( base_structure × material.structure_mult × (armored ? 1.5 : 1.0) )
cost      = round_half_up( frame_cost × material.cost_mult )
          + (armored ? round_half_up(frame_cost × material.cost_mult × 0.5) : 0)
          + Σ component.cost
```

Material multiplies the frame, not component prices. **Armor** is a hull wrap:
no interior space, 1.5× hull HP, costs half the (material-adjusted) frame.
Bigger hulls pay more to plate.

**Shields** are per face (F, FR, RR, R, RL, FL). One bank on a face is one
power that face can hold in battle. Each bank costs 1 and takes 1 space.
In `--yard`, **shields all** steps every face together; ↓ onto a face to
set that face alone. Allocate still lights faces from 0 each turn, up to
the banks you installed.

Hull **size** is still 1–7 (combat silhouette unchanged). Construction space,
frame cost, and base HP use MOO's four-hull decades on sizes 1 / 3 / 5 / 7
(Small / Medium / Large / Huge), with geometric midpoints on 2 / 4 / 6.
Numbers are ×2 vs raw MOO Small so a fighter can mount a compact gun.
`defense` is MOO natural defense. Combat still scales silhouette by `size / 2`,
then shifts the d20 threshold by `(defense − size-2 defense)` so a Destroyer
is unchanged, a Fighter is harder to hit, and a Titan is easier. Path length
is still `max_maneuver_actions` (shown as `mv` in the TUI). No interstellar
map — this is battle agility only.

|---:|---|---:|---:|---:|---:|
| 1 | Fighter | 20 | 4 | 2 | +2 |
| 2 | Destroyer | 63 | 9 | 6 | +1 |
| 3 | Light Cruiser | 200 | 20 | 20 | +1 |
| 4 | Heavy Cruiser | 632 | 63 | 63 | 0 |
| 5 | Battleship | 2000 | 200 | 200 | 0 |
| 6 | Dreadnought | 6325 | 632 | 632 | −1 |
| 7 | Titan | 20000 | 2000 | 2000 | −1 |
Components and their space/cost/stat values are defined only in
`data/components.toml`; hull construction values are defined in
`data/sizes.toml`. Space and cost are design-time constraints and are not
serialized into the runtime ship.

Compact SKUs are a design-time space/cost trade: they compile to the same
combat fields as the baseline kind (`accuracy_bonus` / `damage_bonus` stay 0).
Potent and Precise write those modifiers onto the compiled weapon.

The committed design `data/designs/yard_destroyer.toml` is the small acceptance
fixture; `scenarios/yard_destroyer.toml` is the playable duel. The
compiled catalog files are durable fixtures when referenced by scenarios or
simulation suites; throwaway experiments should use `validate` or `cost`, or
be removed after compiling.
